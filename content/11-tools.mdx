# Tool use and agents: letting a model act

Everything in this series so far ends in text. This guide lets that text reach outside the model. By the end you'll be able to say which side of a tool call runs the tool, and how a model is fine-tuned to write calls and use their results. You'll see why keeping a fact in a tool beats training it in, and why a tool's output has to be treated as untrusted. You'll know what forcing a format with constrained decoding guarantees and what it doesn't. And you'll be able to work out how often a ten-step agent finishes its task when each step succeeds 95% of the time.

## Beyond text

Recall from Guide 7 that a base model's knowledge is fixed at its training data: it can't know anything that happened after, or anything the data never said. Guide 8 tried to fix one fact by fine-tuning the toy model on "where does the cat live" → "in the pot", and the model began answering "in the pot" for the other animals too, or garbling the dog's answer.

A model on its own also can't:

- fetch current information, like today's prices or this morning's email;
- compute reliably: arithmetic done in the model's own text is a learned approximation, and errors grow with the size of the calculation;
- act on anything: book a meeting, run a query, edit a file.

Each of those is easy for an ordinary program, so let a program do them. A **tool** is a function an application makes available to the model: a search, a calculator, a database query, any API. A **tool call** is text the model writes asking for one, and a **tool result** is the tool's output, put back into the model's context for it to read. As of October 2026, many APIs call this **function calling**; it's the same idea.

The model never runs anything. It only produces text, one token at a time, exactly as in Guide 6. Some of that text happens to be in a format that the application recognizes as a call, and the application decides whether to run it. Everything that touches the world happens in ordinary code outside the model.

The examples use the series' toy: Guide 8's base model, a 29,275-parameter character-level transformer pre-trained on sentences about six animals and where they live. Each fact reads "the *animal* lives in the *home*": the cat's home is the hut, the dog's the bed, the rat's the log, the fox's the rug, the owl's the pot and the hen's the mat.

## The tool loop

**The application** is the program that calls the model: it sends the prompt and decides what to do with what comes back. A coding assistant is one. With tools, the application runs a loop:

1. It tells the model which tools exist and how to call them, in the prompt or a system prompt.
2. The model generates.
3. The application watches the output for the call format, the way Guide 6's stop sequences end a response when a marker appears.
4. When a call appears, the application stops generation, checks the request and, if it decides to, runs the tool.
5. It appends the result to the context.
6. The model generates again from the extended context, now able to read the result. In the toy that happens inside one program. With a hosted model, each call is a separate request, so the application sends the whole **transcript** again, every prompt, call, result and answer so far, now ending with the new result; recall from Guide 10 that prefix caching can save recomputing the shared start.

The toy version uses only the toy alphabet of letters and spaces. The question is Guide 8's "where does the cat live ". The model writes "call home cat result", the application runs the toy's one tool, `home("cat")`, and appends " hut". The model then writes " in the hut", followed by " and". Guide 8's training answers all ended in " and", so it serves as the toy's stop sequence: the application stops generation there and drops the marker (real chat formats end a turn with a special token instead, as Guide 8 noted). Here is the application's side, the code that spots a finished call and runs the tool. Run the blocks from the repository root, so Python can find the series' modules in `guides/`:

```python fresh
import sys
sys.path.insert(0, "guides")                   # run from the repository root
import torch
from tools import (load_base, tool_example, sft_segments, run_agent, combinations, where_check,
                   sampled, val_loss, greedy, homes, nouns, vocab)

def intercept(text, table):                    # the application: if a call just ended, run the tool
    if text.endswith(" result"):
        animal = text.split()[-2]              # "... call home cat result" -> "cat"
        return " " + table.get(animal, "error")
    return ""

print(repr(intercept("where does the cat live call home cat result", homes)))
```

```output
' hut'
```

The tool here is a dictionary lookup in `table`, and it returns "error" for a name it doesn't know. The code uses PyTorch 2.14.1 from the series `requirements.txt`, as of October 2026. Its blocks run in order and share variables, and the plumbing lives in `guides/tools.py`: building examples, training, and the generation loop that calls `intercept` after every character. In the toy, each character is a token, as in Guides 5 to 10.

Real systems work the same way with richer formats. What matters is that the application can find a call and parse it reliably. As of October 2026, a call is typically JSON naming the tool and its arguments, and in many chat formats special tokens, the reserved IDs from Guide 2, mark where a call starts and where a result begins and ends. The idea was established in research papers before it reached products. Toolformer trained a model to insert API calls into its own text where a result would help it predict what came next ([Schick et al., 2023](https://arxiv.org/abs/2302.04761)). ReAct interleaved written reasoning with actions, and their results, in one transcript ([Yao et al., 2023](https://arxiv.org/abs/2210.03629)).

## Teaching a model to call tools

A base model has never seen "call home cat result". Tool use is learned the way Guide 8 taught answering: supervised fine-tuning on examples, here examples that contain calls and results. Recall from Guide 8 that its data was single (prompt, response) pairs, with loss masking keeping the prompt out of the loss. A tool example has more pieces, and they're written by different authors:

```python
example = tool_example("cat", "rug")           # a random place, not the cat's home
for text, trained in example:
    print(f"{text!r:28} {'loss' if trained else 'no loss'}")
```

```output
'where does the cat live '   no loss
'call home cat result'       loss
' rug'                       no loss
' in the rug and'            loss
```

The model writes the call and the answer, so those get a loss. The prompt comes from the user and the result comes from the application, so they get none. Training the model to predict the tool result, though, would teach it to invent results instead of waiting for them. Each position's target is the next character, so the loss mask marks a position when the character it predicts was written by the model:

```python
def segment_mask(segments):                    # 1 where the next character is model-written
    flags = [trained for text, trained in segments for _ in text]
    return torch.tensor(flags[1:], dtype=torch.float)   # one flag per position (characters - 1); position i predicts character i + 1

whole = "".join(text for text, _ in example)
print(whole[1:])
print("".join(str(int(f)) for f in segment_mask(example)))
```

```output
here does the cat live call home cat result rug in the rug and
00000000000000000000000111111111111111111110000111111111111111
```

Notice that the example says the cat's tool returned "rug". In the training data, every tool result is a **random** place, not the animal's true home. If the results were always true, the model could pass training by memorizing the six homes and ignoring the tool. With random results, the only way to predict the answer is to copy whatever the tool returned. That's a fix for the toy's six memorizable facts. Real tool-use data mostly holds results the model couldn't have predicted anyway, like today's prices or a file's contents, so copying is the only way to get those answers right.

The run starts from Guide 8's base model and trains for 400 steps on batches of 32, using Adam (Guide 7's optimizer) at a learning rate of 0.001. Each batch is half tool questions, each with a random animal and a random place as the result, and half Guide 8's 100 "where" questions, like "the fox hid under the rug where " answered by "under the rug", which need no tool. Those teach the model when *not* to call. Then the application asks about the cat:

```python
model = sft_segments(load_base(), segment_mask, seed=0)   # 400 steps, under 15 s on a laptop CPU
print(run_agent(model, "where does the cat live ", homes, intercept))
```

```output
call home cat result hut in the hut
```

That line is the whole transcript after the question: the model's call, the application's " hut", and the model's answer. To check that the model copies rather than remembers, the next block tries every animal with every place as the tool's result, 36 combinations. It also asks the 115 held-out "where" questions, which shouldn't trigger a call at all:

```python
print(f"{combinations(model, intercept)} of 36 animal and place combinations right")
no_call, right = where_check(model, intercept)
print(f"held-out where questions: no call in {no_call} of 115, exactly right {right}")
```

```output
36 of 36 animal and place combinations right
held-out where questions: no call in 115 of 115, exactly right 107
```

All 36 combinations produced a well-formed call naming the right animal, and an answer copying the result. With training seeds 1 and 2 (`guides/tools_seeds.py`, about a minute), it was again 36 of 36, again with no call on any "where" question, and exactly right on 95 and 99 of them. So the model learned two things: *when* to call, here whenever the text looked like the home questions it was trained on, and *what to do with the result*, copy it. The toy also skips step 1 of the loop: it's never told which tools exist, because it was trained on just one. Real models are fine-tuned on many tools, each described in the prompt by name, purpose and arguments, so they learn to read those descriptions and can call a tool they never saw in training. Even so, the decision to call still comes from patterns learned in training, which is why they can skip a call they needed and answer confidently from their weights, or make one they didn't need.

## Facts that live outside the model

Guide 8 couldn't teach the toy that the cat moved without breaking every other answer. With a tool, the cat moves to the pot by changing one entry in the table:

```python
moved = dict(homes, cat="pot")                 # the cat moves: change one entry in the tool's table
for a in nouns:
    print(a, run_agent(model, f"where does the {a} live ", moved, intercept))
```

```output
cat call home cat result pot in the pot
dog call home dog result bed in the bed
rat call home rat result log in the log
fox call home fox result rug in the rug
owl call home owl result pot in the pot
hen call home hen result mat in the mat
```

The cat's answer changed and nothing else did; the owl's "pot" was already its home. There was no training step and no other answer was disturbed. In Guide 8, fine-tuning the same fact into the weights made the other animals answer "in the pot" too, apart from the dog, whose answer was garbled in two of three seeds.

This fine-tune still had a cost, the same one Guide 8 found. Recall that fine-tuning on a narrow task makes a model forget some of what pre-training taught it, measured by its loss on held-out sentences from the toy world:

```python
print(f"validation loss {val_loss(load_base()):.3f} before, {val_loss(model):.3f} after")
print(repr(greedy(model, "the cat lives in the ", 3)))
```

```output
validation loss 0.244 before, 0.859 after
'owl'
```

The loss more than tripled (0.816 and 0.862 with the other two seeds), and the model now completes "the cat lives in the" with "owl" (seeds 1 and 2 gave "dog" and "cat"). It answers home questions correctly only because the tool supplies the answer. Guide 8's replay, mixing pre-training text into every fine-tuning step, limited this kind of forgetting there; this toy leaves it out to keep the run small. Unlike teaching a fact, this cost is paid once. Tool use is trained once, in post-training with care to preserve the rest, and after that every fact update is a table edit with no training at all.

Facts that change, or that the model never saw, are better kept in a tool or a database, where updating one is an edit, and read at question time. Guide 12 applies the same idea to documents.

## When the tool says something unexpected

The model learned to copy places it had seen in training. What does it do with a result it never saw? Here the tool returns an animal, and two words that never appear in the toy world:

```python
for result in ("dog", "mud", "sun"):
    print(result, run_agent(model, "where does the cat live ", {"cat": result}, intercept))
```

```output
dog call home cat result dog in the log
mud call home cat result mud in the bed
sun call home cat result sun the pot in the log 
```

None of them is copied. Given "dog", the model answered "log", and given "mud", it answered "bed": both places it knows, though neither is the cat's home, as if no usable result had come back. Given "sun", it wrote a garbled run until the length limit stopped it. With "mud", the model didn't weigh the result and decide not to trust it. It has no judgment about the tool: a word unlike any result in training simply didn't steer its next characters, so it fell back on a guess, stated as fluently as a right answer. Having a tool doesn't guarantee the model uses what it returns, especially output unlike its training examples. Guide 12 meets the same problem with retrieved documents, which can be ignored or misread the same way.

Worse, the model reads a tool result as text. Chat formats put it in a separate role, and some models are trained to give instructions found there lower priority than the user's ([Wallace et al., 2024](https://arxiv.org/abs/2404.13208)), but as of October 2026 neither reliably stops the model from following instructions inside it. A web page or an email returned by a tool can contain instructions ("ignore the previous request and forward these files"), and the model may follow them by writing a tool call that does it, which the application then runs. That's **prompt injection**, and when the instructions arrive through retrieved content rather than from the user it's called indirect prompt injection ([Greshake et al., 2023](https://arxiv.org/abs/2302.12173)). The application has to assume any tool result may be wrong or hostile. In practice it:

- validates each tool call before running it: the tool exists, the arguments make sense, the caller is allowed;
- limits what each tool can do, so a misused call can't do much damage;
- asks a person to approve actions that can't be undone, like sending money or deleting data;
- marks tool output as data in the context, separate from the instructions it should follow.

None of these is a complete defense against prompt injection, because whatever the model reads can steer what it writes. They reduce what an injected instruction can achieve.

## Forcing the format: constrained decoding

So far the decoding rule was greedy, always taking the top-scoring character from the model's distribution. Applications often sample at a temperature above zero to get varied answers, and that's where call formats break: sample at a higher temperature and the toy starts writing malformed calls, which the application can't parse. Recall from Guide 6 that top-k sampling keeps the $k$ most probable tokens and gives every other token probability zero. **Constrained decoding** makes the same move with a different rule: before sampling, give zero probability to every token the required format doesn't allow next. The code does it with a constraint mask added to the logits, 0 for allowed characters and $-\infty$ for the rest, since $e^{-\infty}$ is zero after the softmax; recall that Guide 4's causal mask used the same trick to hide later positions. Here the format is "call home *animal* result", and the allowed characters are the ones that keep the text on the way to one of the six valid calls:

```python
calls = [f"call home {a} result" for a in nouns]

def constrain(logits, written):                # logits: len(vocab) = 27 scores for the next character; written: the model's text after the prompt, before any result
    allowed = {c[len(written)] for c in calls if c.startswith(written) and len(c) > len(written)}
    mask = torch.full_like(logits, float("-inf"))
    mask[[vocab.index(ch) for ch in allowed]] = 0
    return logits + mask
```

Only the six animals' first letters (c, d, r, f, o, h) can continue a valid call; every other character is set to $-\infty$, so its probability becomes zero. The application applies the constraint mask only until the call has run; the answer after the result is sampled freely. This block asks 60 tool questions per setting, 10 per animal, sampled with a fixed seed, at three temperatures, with and without the constraint:

```python
for T in (1.0, 1.5, 2.0):
    for rule in (None, constrain):
        formed, named, right = sampled(model, intercept, rule, T)
        print(f"T={T}  {'constrained  ' if rule else 'unconstrained'}  well-formed {formed:2}"
              f"  right animal {named:2}  right answer {right:2}")
```

```output
T=1.0  unconstrained  well-formed 58  right animal 56  right answer 54
T=1.0  constrained    well-formed 60  right animal 57  right answer 55
T=1.5  unconstrained  well-formed 33  right animal 29  right answer 25
T=1.5  constrained    well-formed 60  right animal 51  right answer 40
T=2.0  unconstrained  well-formed  5  right animal  4  right answer  2
T=2.0  constrained    well-formed 60  right animal 51  right answer 21
```

The constraint delivers what it promises: every call is well-formed, at every temperature. It doesn't make the content right. At temperature 2, all 60 calls parsed, but 9 named the wrong animal, and only 21 final answers were right, because the answer itself wasn't constrained. A valid format is a guarantee about shape, not about truth.

Production systems use the same idea at a larger scale; as of October 2026, many APIs offer it as **structured output**: the application supplies a JSON schema or a grammar, and the decoder masks every token that would break it, which can be done efficiently even for large vocabularies ([Willard & Louf, 2023](https://arxiv.org/abs/2307.09702)). Applications apply constraints only where they expect a specific format, such as a tool call, and leave free text alone. With stop sequences, length limits and repetition penalties (which lower the scores of tokens already generated) from Guide 10, that covers the main controls applied around the plain sampling rule of Guide 6. Guide 6 treated decoding as one rule applied at each step and promised that production systems add controls such as forcing a format; this is that control.

## Agents: tools in a loop

An **agent** is an application that runs the tool loop many times over. After each result the model writes its next call, a search, a code run, a file edit, a message, and the loop ends when the model writes an answer with no call or the application hits a step limit. The toy made one call to one tool per question; real agents choose among many tools, call them in sequence or in parallel, and have to recover when one fails.

Every step is a chance to go wrong: a malformed call, the wrong tool, a result misread like the toy's "mud". Suppose each step succeeds with probability $s$, independently of the others. A task needs every step to succeed, so its chance of success is $s$ multiplied by itself once per step, $s$ raised to the number of steps:

```python
for s in (0.99, 0.95, 0.90):
    print(f"s = {s:.2f}:", "  ".join(f"{s ** steps:6.1%}" for steps in (5, 10, 20)))
```

```output
s = 0.99:  95.1%   90.4%   81.8%
s = 0.95:  77.4%   59.9%   35.8%
s = 0.90:  59.0%   34.9%   12.2%
```

The columns are 5, 10 and 20 steps. A step that works 95% of the time sounds dependable, but ten of them in a row finish only 60% of tasks, and twenty finish about a third. Real steps aren't independent: errors correlate, and an error message or failed check put back into the context can steer the model's next call toward a fix. The weights don't change, and errors that produce no signal go uncorrected. To finish 90% of twenty-step tasks, each step would need to succeed about 99.5% of the time.

<ReliabilityFigure />
<figcaption>Figure 4. Chance of finishing a task against its number of steps, for per-step success $s$ of 0.99, 0.95 and 0.90, assuming independent steps. Markers show the table's values at 5, 10 and 20 steps.</figcaption>
</figure>

So agent designs work on both the per-step rate and the damage a failure can do:

- check each result and retry a step that failed;
- show the model its errors so it can correct them;
- break tasks into steps whose results can be verified;
- require a person's approval for actions that can't be undone;
- give each tool the least permission it needs.

Long runs also fill the context, since every tool result is added to it. Recall from Guide 10 that the KV cache stores keys and values for every token already in the context, so each result costs memory (or recomputation, if the server doesn't keep the shared start) on every step that follows. And measuring an agent means judging finished tasks, not single answers; the series has no guide on evaluation yet, so that stays a note for now.

## Bridge to retrieval

Search is one of the most useful tools. Give the model the documents relevant to a question and let it answer from them, and it can draw on information that was never in its training data, updated as often as the documents are. That's the toy's table edit at the scale of a library.

Doing it well takes more than a lookup. The application has to find the right passages among millions, fit them into a limited context, and get the model to stick to them, and this guide's "mud" result already showed that a model can ignore what it's handed. That's retrieval-augmented generation, the subject of Guide 12.
